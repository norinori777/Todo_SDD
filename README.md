## プロジェクトの目的

FlutterとDartを使用し、Android向けのMarkdown Todoアプリを開発します。
ユーザーが指定したフォルダー内のMarkdownを正本とし、
Obsidianで管理しているTodoを参照・作成・更新できるようにします。

## 憲法に含める原則

1. 要件とユーザーデータの保護
   - requirements.mdを機能要件の参照元とする。
   - 既存Markdownの編集対象外の内容、タグ、階層タグ、
     Wikiリンク、frontmatter、書式を意図せず失わない。
   - 読み込み・保存・権限のエラーを成功として扱わない。
   - 複数ファイルを更新する場合は、部分的な失敗と整合性を考慮する。

2. 機能単位のアーキテクチャ
   - Todoや設定などの機能ごとにコードを整理する。
   - Todo固有のRepository、モデル、画面などは
     features/todo/ 内に配置する。
   - 機能間の連携は公開インターフェースを通じて行う。
   - Markdownの読み書きと解析はデータアクセス境界に集約し、
     UIにファイル操作や解析の詳細を持ち込まない。
   - 機能横断の共通処理だけを共通領域に置く。

3. シンプルで保守しやすい実装
   - 現在の要件に必要な範囲で設計する。
   - 不要なサーバー、API、データベース、抽象化、
     コード生成や依存パッケージを追加しない。
   - コメントは自明な処理の説明ではなく、
     非自明な理由や制約の説明に使う。

4. 振る舞いとデータ保護を重視したテスト
   - Flutter標準のflutter_testとintegration_testを使用する。
   - 変更に応じて単体・Widget・結合テストを選択し、
     正常系だけでなく保存失敗やデータ保持も検証する。
   - テスト用の依存を置き換える場合は、まずFakeを検討し、
     相互作用の検証などで必要な場合にMockを使用する。
   - 統合テストの標準コマンドはflutter test integration_testとする。
   - 一律のカバレッジ率より、重要な振る舞いと失敗経路を重視する。

5. 日本語でのコミュニケーション
   - プロンプトのやり取りと、作成するドキュメントは日本語とする。
   - コードの識別子、コマンド、技術用語は適切な表記を維持する。

## ルールとスキルの扱い

- 憲法には、agents/rules/flutter-todo/README.md を入口とする
  開発ルールの参照インデックスを記載する。
- ルールの詳細を憲法にすべて複製せず、
  原則と各ルールへの参照を整理する。
- .github/skills/ のスキルは該当する作業で参照する手順とし、
  すべてのスキルや技術を無条件に適用しない。
- スキルの例とプロジェクトのルールが食い違う場合は、
  プロジェクトの憲法・ルールに沿うように判断する。
- 要件・憲法・ルールの間に矛盾がある場合は、
  一方を黙って変更せず、矛盾と影響を報告して確認する。

## 不明点の扱い

要件に未定義または曖昧な箇所がある場合は、独自の仕様を確定しないでください。
特に、Todoの識別表記、完了状態の保存形式、削除の方法、
タグリンク押下時の動作、関連情報のリンク方法は、
必要に応じて確認事項として整理してください。
