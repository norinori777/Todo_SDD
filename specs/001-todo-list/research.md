# Phase 0 調査: Todo一覧画面

## データの正本とアクセス

- **決定**: 指定フォルダー以下のMarkdownを正本とし、再帰探索結果をメモリ内の一覧に投影する。Androidでのフォルダー選択・永続権限は設定機能の公開境界から受け取り、保存先を含むアクセスを指定フォルダー内に限定する。
- **理由**: FR-001、FR-014と憲章I・IIIにより、DBや同期サーバーは不要。Androidの共有ストレージではフォルダーアクセスの権限と提供元の能力を実機で検証する必要がある。
- **代替案**: パスを直接要求する方法はAndroidのアクセス制限と権限継続を保証できない。DBへの複製を正本にする方法は外部編集との整合性と要件に反する。

## Markdownの解析と保持

- **決定**: 読み取りではfrontmatterのYAML構文・`tags`型を検証し、仕様で除外された領域を識別したうえで、タグとWikiリンクの位置を取得する。書き込みでは元テキストを再構築せず、対象タグの範囲だけを編集する。未対応形式、解析失敗、位置を安全に特定できない場合はファイルを除外または更新を拒否して理由を表示する。
- **識別表記の決定**: 旧Markdown互換ルールの`# TODO`表記とFR-002が矛盾していたため利用者に確認し、`#todo`を識別し`# TODO`見出しのみでは識別しないFR-002を採用した。[Markdown互換ルール](../../agents/rules/flutter-todo/data-markdown-compatibility.md)も整合させた。
- **理由**: 汎用のMarkdown/YAML再シリアライズはコメント、順序、引用、改行などを変え得る。FR-002、FR-009、FR-010、FR-013に両立が必要。
- **代替案**: 正規表現だけで全形式を一括処理する方法はコード・コメント・エスケープ・リンクの判別や編集対象外の保持を保証しにくい。利用ライブラリは位置情報と保存形式保持、ライセンス、Android対応を実装前に評価し、要件を満たす場合のみ追加する。

## 通常のMarkdownリンクの部分編集

- **決定**: リンク先と表示文字を別の構文領域として扱い、リンク先のタグ表記は判定対象外、表示文字中のタグは対象とする。表示文字が`#完了`だけの場合はリンク先を表示文字にし、表示文字中の`#`をエスケープする。元のリンク先・タイトル・参照先定義や対象外の書式は保持する。参照形式は対応する定義を解決してから扱い、範囲や保存後のリンク先を安全に確認できない場合は更新を拒否し理由を通知する。
- **理由**: [CommonMarkのリンク構文](https://spec.commonmark.org/0.31.2/#links)ではリンク先・表示文字・タイトルの区切りとエスケープが異なり、[バックスラッシュエスケープ](https://spec.commonmark.org/0.31.2/#backslash-escapes)や文字参照の解釈もある。リンク先を単純に表示文字へコピーすると、角括弧やバックスラッシュなどで構文や表示が変わり得る。FR-002、FR-008、FR-009とデータ保護を両立するため、生成した表示文字の構文とリンク先を検証する。
- **代替案**: 対象リンク全体の再シリアライズや一括置換は、タイトル、参照定義、エスケープや無関係な書式を変え得るため採用しない。

## 状態更新の安全性

- **決定**: 読み込み時の元データと対象識別子を保持し、保存直前に再取得した内容と比較する。不一致なら書き込まず再読み込みを促す。保存は元ファイルの破壊を防ぐ能力が検証された方式に限り、未確認または利用不能なら明示的に更新を拒否する。状態は永続化成功後にのみ確定する。
- **理由**: FR-008、FR-009、FR-013、FR-015は外部変更と保存失敗の双方に対応する。単なる事前比較は比較直後の競合や途中書き込み失敗を防がず、一般的なAndroidドキュメント提供元の書き込み・リネームが原子的とは限らない。
- **代替案**: 対象への直接上書きや無条件のリネームを安全とみなす方法は、部分書き込みや競合で元データを失う可能性がある。対象環境で原子性・排他または同等の保証が証明できなければ保存機能を有効化しない。競合検出と保存の間の競合に対する保証範囲を、具体的なストレージ方式と共に検証する。

## 検索と関連付け

- **決定**: タイトルは英字の大文字・小文字を区別しない部分一致、タグは大文字・小文字を区別する完全一致。通常は未完了のみ、`#完了`は完了のみ。タイトルはUnicodeコードポイントの辞書順で昇順、同名は相対パス昇順とし、タイトル検索時の英字の照合とは独立して扱う。Wikiリンクは指定フォルダーを基点とするパスまたはノート名で直接関連付け、双方向を重複排除する。一意でない・存在しない・読めない対象は誤ったノートを開かず通知する。
- **理由**: FR-006、FR-010、FR-013、FR-017と仕様のAssumptionsに合う。
- **代替案**: 曖昧な同名候補から最初の1件を選ぶ方法やリンクの連鎖をたどる方法は仕様に反する。
- **並び順の注意**: Dartの[`String.compareTo`](https://api.dart.dev/dart-core/String/compareTo.html)はコード単位で比較するため、補助平面文字を含む文字列ではUnicodeコードポイント順と一致しない場合がある。タイトルはコードポイント列で比較し、例えばU+E000がU+10000より前となる境界をテストする。

## 状態・検証

- **決定**: 一覧状態は検索条件、ロード結果、個別の失敗、関連情報の展開状態を区別し、別画面から戻るたびに条件を保って再読込する。Flutter標準の単体・Widget・integration testと実ファイルテストを使い、TDDで進める。
- **理由**: FR-013、FR-016、SC-001〜006および憲章IVに合わせ、空結果と失敗を混同しない。
- **代替案**: Fakeのみの検証は実際のファイル破損・権限・Android提供元の動作を確認できない。性能値をデスクトップの模擬試験だけで代替することもできない。

Flutterプロジェクトと依存関係は既に存在する。安全な保存の実現可否は対象のAndroidストレージ提供元で検証するまで保証しない。

## 性能と利用者評価

- **決定**: SC-006は、Core i7-13700H・メモリ16GB・Windows 11のホスト上でAndroid 17のPixel 9aエミュレーターを使う。指定の10フォルダー、各20,000バイトの未完了Todo 1,000件、循環するパス付きWikiリンクを仕様の固定規則で用意し、仮想CPU 4個・メモリ4GB・GPUハードウェア支援で測る。測定ごとにエミュレーターを再起動し、初回読込・並べ替えが完了し操作可能になるまで3回測り、すべて10秒以内を合格とする。検索と関連情報の利用者評価はそれぞれ10人で行う。
- **理由**: ファイル数、Todo数、測定終了時点と実行環境を揃え、SC-002、SC-004、SC-006の判定を再現しやすくする。エミュレーターでの合格は実機の性能保証を意味しない。
- **代替案**: 最初の数件だけの表示時間、件数や保存先を固定しない測定は、全件を利用できるまでの性能を比較できない。

## 実装時のライブラリー・アクセス評価

- YAMLの構文検証にはDart製の [`yaml` 3.1.4](https://pub.dev/packages/yaml/versions/3.1.4) を採用する。MITライセンスで、Dart 3.11.5とAndroid向けFlutterで利用でき、`YamlNode.span` により元テキストの位置を参照できる。ただしYAMLの出力機能はなく、位置情報だけで全形式の安全な部分編集が保証されるわけではない。編集範囲を安全に特定できない場合は更新を拒否する。
- [`markdown`](https://pub.dev/packages/markdown) はBSD-3-ClauseライセンスのDart製ライブラリーだが、公開説明はMarkdownからHTMLへの変換を主とし、仕様のWikiリンクや書式を保った部分編集を保証しない。現時点では追加せず、必要な構文・位置の扱いはテストで検証する。対応外の構文を安全に扱えないときは拒否し、再シリアライズしない。
- Androidフォルダーへのアクセスには、プラットフォーム標準の [Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files) と永続URI権限を公開境界経由で利用し、外部プラグインは追加しない。読込はAOSP外部ストレージ提供元（`com.android.externalstorage.documents`）に限定する。各項目を読む前に `DocumentsContract.isChildDocument` と `findDocumentPath` で親子関係と正規化後の階層を検証し、リンクや階層不一致を拒否する。この提供元の `FileSystemProvider` は子判定と文書パスの解決に正規化済みファイルパスを使う（[AOSP実装](https://github.com/aospapp/aosp/blob/main/frameworks/base/core/java/com/android/internal/content/FileSystemProvider.java)）。他の提供元は同等の挙動を個別に検証できるまで読み込みを拒否する。保存の原子性や競合保護は別途実機検証が必要で、保証できない書き込みは拒否する。
- ローカルファイル読込のWindows検証には、既存の生成済みAPIバインディングを利用できる [`win32` 5.15.0](https://pub.dev/packages/win32/versions/5.15.0)（BSD-3-Clause）と `ffi` を追加した。開いたファイルの最終パスをハンドルから確認し、同じハンドルで読み込む。固定NTFS以外や別ボリュームを拒否し、リンクを含むルートと差し替えを検証する。AndroidはWindows専用実装を使わず、検証済みの外部ストレージ提供元だけをSAF経由で読み込む。Android提供元の統合検証が完了するまではT009を未完了とし、一般のSAF提供元では閲覧も有効化しない。

## Unicodeと文字コード

- **決定**: 元のバイト列を保持し、UTF-8の厳密な検証とUTF-8 BOMの検出を行う。別形式のBOM、不正なUTF-8は除外して通知する。タグ検索だけでNFCへ正規化し、Android標準の[`java.text.Normalizer`](https://developer.android.com/reference/java/text/Normalizer)を利用するプラットフォーム境界で複数タグをまとめて処理する。比較以外には正規化結果を使用せず、元のファイルと表示は変えない。
- **理由**: FR-001、FR-006、FR-009に加え、既存のDart SDKに正規化APIを仮定しない。Android側の実装とDart側の検索は、結合濁点やASCIIの大小文字を含む実端末テストと単体テストで確認する。未対応プラットフォーム・変換失敗を未正規化の成功結果に変換しない。
- **代替案**: 正規化せず比較する方法は同一視の要件を満たさない。外部ライブラリーの追加は現時点では不要であり、Android以外の実行が将来必要になった場合は再評価する。

## 中断復旧と競合の設計

- **決定**: 提供元ごとの保存能力を、対象の識別子・読み込んだ版・新旧の完全なバイト列に基づく条件付きコミット、復旧データの耐久性、権限、範囲制限として評価する。復旧情報は選択フォルダー内に衝突しない専用領域として確保し、他のノートと区別して探索対象から除外する。元・更新後の内容と操作状態が耐久化されたことを確認してからコミットを試み、完了を確認するまで復旧情報を保持する。専用領域を安全に確保・識別できない場合も書き込みを拒否する。
- **理由**: FR-009、FR-014、FR-015は、途中終了後も完全な内容を復元可能とし、外部変更と競合したときに双方を保持することを求める。復旧時は対象と復旧情報を再読込し、現在値が復旧処理由来か外部変更かを安全に判定できない場合も自動上書きしない。両方の全文確認後に利用者が選択し、適用直前に再び競合を検査する。読取不能時は選択・書き込み・復旧情報の削除を行わない。
- **代替案**: 一時ファイルや事前比較だけを安全性の証明とする方式は、競合や電源断に対する保証がない。共通SAF APIによるすべての提供元への保証は前提にしない。対象の実際の提供元で条件付きコミットと耐久性を証明できなければ閲覧専用のままとし、少なくとも一つのAndroid保存先でSC-003を満たせなければ公開しない。
- **公式契約と残るリスク**: [DocumentsProvider](https://developer.android.com/reference/android/provider/DocumentsProvider)のファイルオープンはモードの動作が提供元によって異なり、[DocumentsContract](https://developer.android.com/reference/android/provider/DocumentsContract)の一般契約から原子的置換、外部アプリを含む条件付き確定、停止後の耐久性は保証できない。変更通知や最終更新時刻の事前比較、一時ファイルへの書き込みは競合のない確定の代替にならない。条件を満たす具体的なAndroid提供元とAPIはまだ特定できていないため、その証拠とSC-003の実地検証を公開前に揃える。独自DBを正本にする代替案はMarkdownを正本とする憲章・仕様に反するため採用しない。
